# tools/ —— 生成、截图与**动画量化验证**

前几个脚本负责「把页面画出来给人看」，后几个负责「证明它真的在动」。
两者不能互相代替：截图只能证明某一刻画面是对的，证明不了它在动；
而「在动」这件事，肉眼在没有录屏的情况下同样说不清楚。

## 一览

| 脚本 | 作用 |
| --- | --- |
| `shot.js` | 无头 Chrome 开页 → 执行一段 JS → 截图 + 回收控制台/错误 |
| `look.sh` | **定点观察**：镜头对准世界坐标 (x,y,scale)，冻表后截一帧（含雨量/行人/分片数） |
| `fig-sheet.js` | 把行人 `_figure` 单画在白底上（大比例逐帧），调人物形准用 |
| `probe.js` | 问页面要运行时状态（行人世界/屏幕坐标），**并同时存下那一帧** |
| `pair.js` | 同一会话里冻出两个时刻各截一帧（只改 `alive.t`，其余不变） |
| `isolate.js` | 把某个动画物体从灵动层**隔离**出来，取四帧做对照 |
| `make-shots.sh` | 批量出 `shots/` 下十张展示图 |
| `smoke.sh` | 功能冒烟：拖拽/滚轮/键盘/小地图/卡片/灵动开关全跑一遍 |
| `freeze-check.js` | **校验冻表是不是真冻住了**（一切像素证据的前提） |
| `anim-proof.py` | 读 isolate 的四帧 → 物体像素/区域归因/横向位移 |
| `diff-bands.py` | 两帧差异按高度带统计（支持按世界坐标分带） |
| `flow-check.py` | 测纹理的整体位移方向（下落 / 上浮 / 原地明灭）——**纵向** |
| `flow-x.py` | 测纹理的**横向**位移量（河的流向与流速），配 isolate 的 water 层 |
| `check-fixes.js` | 在页面内调**渲染用的同一份函数**做验收（往复运动 / 人的构成 / 数据位置） |
| `weather-check.js` | **跨视距**量天气层：雪粒/雨丝在屏幕上的真实尺寸、雾的白纱厚度、各季带被盖掉多少色 |

统一环境（**全部走环境变量，默认用 PATH 上的命令；换台机器不用改脚本**）：

```bash
NODE="${NODE:-node}"      # 有 Node 18+ 即可（shot.js 靠内置 fetch + WebSocket 连 CDP）
PY="${PY:-python}"        # 只有跑像素分析的脚本需要，且要 pip install pillow
URL="${URL:-http://127.0.0.1:8788}/"   # 静态服务地址，端口被占就换一个

# 前置：项目根目录起一个静态服务（不需要任何后端）
python -m http.server 8788 --bind 127.0.0.1
```

无头 Chrome 默认按 Windows 常见安装位置找，其他平台/安装位置用 `CHROME=<path>` 覆盖：

```bash
CHROME="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  "$NODE" tools/shot.js http://127.0.0.1:8788/ out.png 3000
```

## 验证一个「动画到底动没动」的标准流程

### 0. 先验前提：冻表真的冻住了吗

```bash
"$NODE" tools/freeze-check.js "http://127.0.0.1:8788/" "<摆视角的JS>" 3
```

它会冻结后连截 3 张、逐字节比较。**不是全同就别往下做** ——
后面所有结论都建立在「两帧之间只有我改的那个变量不同」之上。

> 这一步是被坑出来的：曾经以为测到了瀑布，其实测到的是 `#intro` 遮罩的
> CSS 动画（`riseIn` / `sealPulse`）。DOM 覆盖层的动画与 `alive.t` 无关，
> 却一直在往像素差异里掺东西。修法是冻结时进入**纯画布模式**：
> 把 `body *` 里所有不含 canvas 的元素 `visibility:hidden`，只留画布。

### 1. 隔离：把目标物体单独摘出来

```bash
"$NODE" tools/isolate.js "http://127.0.0.1:8788/" <target> shots/_diag/iso-x 1.0 2.6 \
  "e.focusOn(<世界x>,<世界y>,<视距>,0.01); await sleep(800);" 1280 720
"$PY" tools/anim-proof.py shots/_diag/iso-x 6 --expect vertical
```

`target` 可取 `waterfall | boat | sail | lotus | water | reeds`，
以及**任何 `SceneData.MOTIFS` 里的点景类型**（如 `dog` / `hen` ——
走的是「按 type 过滤 MOTIFS」那条通用分支，新增点景不用改 isolate.js）。
它产出四帧，构成一组干净的对照：

```
A_full = 背景(tA) + 物体(tA)      A_off = 背景(tA)
B_full = 背景(tB) + 物体(tB)      B_off = 背景(tB)
```

于是：`diff(A_full, A_off)` = **物体占据的像素**（位置不靠肉眼猜），
`diff(A_off, B_off)` = 该处**背景自身**的变化，
两者之差就是**归因于物体自身**的变化量。

`--expect vertical|horizontal` 声明该物体**该往哪走**：
竖直的（瀑布）横向必须钉住，水平的（河水）横向必须明显移动。
不声明就只报数值，不下结论 —— 否则会把「河在流」误判成故障。

### 2. 需要方向、不需要精度时

```bash
"$NODE" tools/pair.js ... A.png B.png <tA> <tB= tA+小Δt> "<摆视角>"
"$PY" tools/flow-check.py A.png B.png x0 y0 x1 y1 [r]
```

> **局限**：对**稀疏细线**纹理（瀑布那 24 条水痕，信号只有几百像素），
> 逐列互相关定位不出位移。这类情形直接**在页面里复现渲染所用的位移公式**
> 核对方向与步长，比在像素上猜可靠得多（本项目就是这么拿到
> 「Δt=0.05s 内 24 条水痕全部下移、平均 11.2 屏幕px」的）。

### 3. 横着流的东西要**换轴**，并且要位移量不只是质心

`flow-check.py` 是给瀑布写的，逐列做**纵向**互相关。拿它测河，**永远报 0** ——
那不是「没动」，是**测错了轴**。`anim-proof.py` 的质心判据能回答
「往哪动」，回答不了「动多快、几层是否一致」。

```bash
# ① 隔离水层（isolate.js 的 water 分支会覆盖 alive._water）
"$NODE" tools/isolate.js "http://127.0.0.1:8788/" water shots/_diag/w 1.0 2.6 ""
# ② 逐行平均成 x 剖面 → 归一化互相关。y0/y1 是**屏幕**行号（世界 y × scale）
"$PY" tools/flow-x.py shots/_diag/w 1.0 2.6 515 605 90 0.8
# ③ 换一个 Δt 再测一遍 —— 两次速度必须一致（见坑 9）
"$NODE" tools/isolate.js "http://127.0.0.1:8788/" water shots/_diag/w2 1.0 2.2 ""
"$PY" tools/flow-x.py shots/_diag/w2 1.0 2.2 515 605 90 0.8
```

实测：两次独立测得 **33.73 / 33.74 世界单位/秒**，与配置值 `FLOW.speed = 34`
吻合 —— 既证明了「河真的在流」，也证明了「只有一个流速」。

## 验收天气层：`weather-check.js`（**跨视距**量同一件事）

```bash
"$NODE" tools/weather-check.js            # 默认打 127.0.0.1:8788
```

它在**三档视距**（观察 0.8 / 中间 0.36 / 整卷概览 0.094）各跑一遍，
每档把雾 / 雪 / 雨**三层各自隔离**画到 fx-canvas 上，然后**真读 alpha 通道**：

| 指标 | 含义 |
| --- | --- |
| `cover8 / cover40` | 覆盖了多少像素 |
| `meanA` | 全屏平均不透明度 —— 这就是「白纱有多厚」 |
| 连通块尺寸 | 雪粒直径（点状块）、雨丝长度（细长块） |
| **单颗粒子包围盒** | 只留一颗粒子在画面上，它自己的 bbox 就是它的屏幕尺寸 |
| **各季带饱和/亮度** | 静态层原色 vs 叠加天气层之后的颜色 → 「颜色被盖掉几个百分点」 |

末尾给出 5 条 PASS/FAIL 不变式（雪不随缩小消失、雨丝尺寸 = 世界长 × 视距、
概览下雾不罩冬景、干燥天冬带不掉色、雪粒不过大）。

### 为什么必须跨视距

世界锚定的粒子（雪 / 雨 / 落花 / 飞鸟）尺寸是**世界尺寸**，
画的时候必须 `× s`。**漏乘 s 在默认视距下几乎看不出来** ——
本项目旧代码把雨丝的长度与线宽写成了固定屏幕像素，
s=0.8 时「看着正常」，缩到概览就变成 1.4px 宽、40px 长的巨条：
实测一条雨丝横跨 **8.6 倍画卷高度**，整幅画糊成灰。

### 坑（本项目实测）

15. **「屏幕锚定的覆盖层」在缩小时会相对放大**。云雾按屏幕走（视差、大小
    与视距无关）本身是对的，但缩到整卷时画面上挤着 12000 世界单位，
    同一团雾相对**内容**就放大了 8 倍 —— 冬景那一带被整片罩白。
    修法：浓度乘一个随视距的收敛系数（`sqrt(s/fit)` 收在 0.34，
    用开方而非线性：中间视距只该轻收，线性会一下把雾收没）。
16. **四季并置的长卷里，「现在是什么季节」不是全局量**。旧代码按**视口中心**
    取一季的配置；缩到整卷时视口中心落在世界 6000（秋），
    于是**冬天那一带开始飘秋天的落叶、一粒雪也不下**。
    正确做法是每颗粒子问自己脚下那片地的季节（`_pickX` / `_want` 按各季
    可视宽度加权），雾也按自己脚下的世界 x 取浓度（夏湿冬薄是地理属性）。
17. **量尺寸前先排除「会连成一片」的东西**。雨密的时候相邻雨丝首尾相接，
    最长连通段量到的是「一串雨」不是「一滴雨」（实测 720px = 整屏）。
    两条对策：**只留一颗粒子在画面上**（bbox 即尺寸）；取点时避开
    画面上半部（雨天灰纱在上 40% 会压过检出阈值，雨丝一落进去就和灰纱连成一块）。
18. **包围盒比几何长度多出一截**：圆头端帽各伸出半个线宽 + 约 1px 抗锯齿，
    合计 ≈2.5px。所以「尺寸是否随视距缩放」的判据要用**绝对误差**（≤2.8px），
    不能用比例 —— 概览时雨丝几何长只有 4.4px，这个常数会盖过比例误差。
    改动前那一项误差是 **36px**，一眼分得开。
19. **粒子尺寸的下限是刻意打破「与视距无关」的**。概览下 1.1 单位的雪粒
    只剩 0.09px，整层雪会凭空消失 —— 于是冬景退成一片没有雪的灰蓝。
    所以给雪粒 / 花瓣 / 飞鸟**托一个 0.5~0.9px 的下限**：
    代价是概览时它们相对画卷偏大，收益是「这一季还在」。
    **这是一处有意的取舍，不是漏乘 s**，判据里要写明。

## 验收一类报修：`check-fixes.js`

像素工具验的是「画面在变」，验不了「**构成**对不对」「**往复运动**有没有行程」。
这类问题直接在页面里调**渲染时用的那一份函数**（`Motifs.boatBob`、`alive.probe`、
`SceneData.MOTIFS`），返回 JSON 断言：

```bash
"$NODE" tools/shot.js "http://127.0.0.1:8788/" shots/_diag/checks.png 2600 \
  "$(cat tools/check-fixes.js)" 1280 720
```

它一次回答四件事：
- 船的**行程 / 最大速率 / 换向**（往复运动不能只取两个 t —— 会撞上折返点，见坑 10）
- 卷首视口里**每个人的 kind**，并在 `t = 0 / 18 / 40` 三次采样确认构成稳定
- 客栈在数据里的位置，以及**卷首视口内**有没有
- 行人速度分布（覆盖率保证要求一律相同）

## 踩过的坑（都是真金白银换的）

9. **互相关的符号要拿合成信号自测**。写 `pa[lo:hi]` vs `pb[lo-d:hi-d]` 得到的 d
   对应的是**向左**移 d，本项目第一版符号写反了。
   自测**不能用脉冲串**（周期信号在 d 与 d±kT 上相关都是 1.0，峰不唯一，
   会测出 −2T 且「相关 1.0000」）—— 要用**平滑随机噪声**。
10. **栅格状纹理有周期混叠**。水线按 22.2 屏幕px 间距铺；
    若真实位移落在周期整数倍附近，会给出等高的假峰，而算出的速度**仍然像对的**。
    判据：**换一个 Δt 再测，两次速度必须一致**。
11. **位移量要声明在世界坐标还是局部坐标里**。物件常用 `ctx.scale(-1,1)` 翻转，
    此后 +x 指向画面左边：照搬 `translate(dx)` 会让翻转过的物件**倒着走**。
    修法 `ctx.translate(m.flip ? -dx : dx, dy)`。
    （本项目 5 条船里 3 条 flip=1；±3.4 的横漂时代看不出来，换成 ±280 的巡航就一眼可见
    —— **小幅度会掩盖坐标系错误**。）
12. **往复运动换向时，依附物要跟着换边**。船尾浪痕原本固定拖在左侧，
    船一回头浪痕就跑到船头去了。修法：按 `navDir` 镜像，浓度随 `|cos|` 收
    —— 换向那一刻速度恰好过零，把浓度收到 0，翻转那一帧就看不见了。
13. **注释里的倍率必须与算式对账**。水面上四层会平移的相位各乘了不同系数
    （1.5 / 1.85 / 2.3 / 0.4），互相剪开＝「在闪」而不是「在流」；
    其中两处的**注释与算式说的不是一回事**（注释写 1.4 倍、算式给 0.6 倍）。
    这类不一致往往是成片的，改一个流速旋钮时**顺手全核一遍**。
14. **「让某类东西出现」要考构图，不能靠相位**。流动对象（行人）出现谁全凭相位，
    多塞人不解决问题；要另起一层**定点**的（常住村民），放在地标旁边。
    本项目一开始把人放在卷首、把客栈放在 x=5560，**两者根本不同框**，等于没修。

1. **`mask` 之后必须重绘**。只改数据不调 `draw()`，画布内容没变，四帧
   自然一模一样 —— 会得出「该物体根本没被画出来」的错误结论。

2. **分带要按世界坐标，不能按屏幕像素硬编码**。视距一换，「河面」那一带
   就落到树上去了。长卷的真实布局是固定的：
   `山脚 ridgeBase=582 / 岸线 shore=632 / 水底 waterBottom=776`。
   `diff-bands.py --view <viewY> --scale <s>` 会把世界带换算成屏幕带。

3. **无头 Chrome 的 rAF 只有 ~11fps**（一帧 ≈89ms），所以
   「固定 `sleep(400)` 后取快照」这种写法本身就是脆的：一个 `dur=0.24s` 的
   缩放动画要跑 3 帧。改成**轮询引擎自己的状态位**（`scaleAnim` /
   `focusAnim` / `vel` / `queue` 都落定）再快照。`smoke.sh` 里还顺手把
   实测帧率记进报告 —— 它是解释一切时序的前提。

4. **断言要「快照比快照」**。拿 `toFixed(4)` 后的快照值去比
   `e.view.scale` 的原值（如 `0.322931…`），会因 3e-5 的差判不等，纯假阴性。

5. **别用一阶差分做高通**。水痕是 `createLinearGradient` 画的「0→亮→0」
   平缓鼓包，不是锐利边缘，`np.diff` 之后幅值几乎为 0。改用「减去大尺度
   移动平均」。

6. **静态叠层会锁死互相关**。瀑布身上三层静态细流两帧里逐像素相同，
   互相关被死死拽在 `dy=0`。先隔离（`A_full − A_off` 取负部只剩暗痕）再测。

7. **给树用的风剪切不能套到瀑布上**。`paintAll` 对所有非舟船的灵动点景统一
   加了 `ctx.transform(1,0,-windTilt,1,0,0)`；瀑布局部 y 从 -234 到 +10，
   剪切后瀑口被横向推开十几个像素、周期 5.7 秒地摆 —— 读起来就是
   「一匹白绸在飘」。判断这类问题的量化口径：**横向质心随时间是否漂**
   （修复前会漂，修复后 0.05px）。
   同理，**鸡也不能套风剪切**：它站在桑树颠（局部原点即脚），一加剪切就
   被吹离枝头。所以 `paintAll` 里活物走单独一支：只给一口「活气」
   （鸡 = 引颈一伸一缩，犬 = 抬头一顿一顿），位移都在 1px 上下。

8. **灵动层整层盖在静态层之上，「越靠观者越晚画」的直觉在这里不成立**。
   静态层（分片烘焙）在下面那块 canvas 上，灵动层是另一块、永远在上。
   于是**任何灵动点景都会盖住所有静态点景**，跟两者的 y（远近）无关。
   本项目就栽在这上面：桃花林（要随风摆 ⇒ 只能进灵动层）按 y=632 横铺
   1880~2780，把整座 606~622 的村子（静态）全埋了 —— 截图里只剩一片粉。
   两个正确的修法：
   - **错开屏幕带**：把要露出来的静态物移到灵动物的**上方或下方的空带**里；
   - **切开区域**：把灵动批量区在该静态物处**断口**（桃花林在桑树 2160~2372 留白），
     否则「鸡鸣桑树颠」的鸡会埋在花里。
   判据很好拿：`look.sh` 对准那个坐标截一张，看目标还在不在。

9. **同一块画布里「大而密」会吃掉「小而疏」**。桃花林第一版 `n=17 / 叶径 2.4`，
   在 900 宽的区间里铺成一道粉墙。改成 `sz` 分片（村后那片压到 0.52、
   叶径降到 1.9）之后，才既有「夹岸数百步」的气势、又不淹没屋舍。
   密度是个乘积（`n × 单株叶点 × 叶径`），调的时候要一起看。

10. **微动不要用整体 `translate`，要绕「该动的支点」转**。
    狗原本写成 `translate(sin·0.9, 0)`（整体横移 0.9 世界单位）——
    本意是「一顿一顿地吠」，实际读出来是**滑步**；而且自检直接判负：
    「声明竖直、却整体横移 **2.2px**」。换成**绕身体重心**俯仰
    （`translate(5,-9) → rotate → translate(-5,9)`）后，

    鸡同理：绕**脚**（局部原点）做引颈的一伸一缩，脚钉在枝上（Δ0.63px）。

    > **横移**和**绕支点俯仰**在像素总量上一样「在动」，只有质心位置分得开。
